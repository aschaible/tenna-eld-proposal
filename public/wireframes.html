Before the screens

Five product decisions gate the interface design.

From Luke's follow-up to the August 13 kickoff: "the data guidelines Jose mentioned will fall out of a handful of product decisions, so I'd suggest we point the session at those directly." Here they are in his dependency order; each card names the screens it gates, and each is recorded as an open entry in the decision log. Anything not decided Thursday leaves the room with a named owner and a date.

P1

Driver account model: full Tenna users, or a stripped-down driver credential?

Are ELD drivers full Tenna users, or a lighter-weight driver credential that exists mainly for the ELD? Luke's note: "Most of the interface design hangs on this one." It decides where the driver record lives, what D1 asks for, and whose profile D23 displays.

A · Full Tenna users Driver identity, profile, and permissions live in Tenna; the ELD reads them through the purpose-built API. One roster, one admin surface.
B · Stripped-down driver credential The ELD owns a lightweight driver record; Tenna sees drivers only where a workflow needs them. Faster to stand up, second roster to manage.

Recorded as P1 in the decision log ↗

Authentication follows from the account model
P2

Authentication: Tenna Cognito/OIDC, or ELD-owned auth with a trusted-peer link?

Follows directly from P1. If ELD users are Tenna users, the app integrates with Tenna's existing authentication (Cognito/OIDC). Alternatively, the ELD handles its own user authentication and the two systems communicate as trusted peers.

A · Tenna Cognito / OIDC D1 becomes an OIDC flow against Tenna's identity provider; sessions, MFA, and password policy are inherited.
B · ELD-owned authentication The ELD issues and validates its own credentials; a trusted system-to-system link carries identity claims between the two platforms.
Gates D1D3

Recorded as P2 in the decision log ↗

Independent of identity: the data question
P3

Telematics point data: does Tenna retain it at all, and if so, where is it processed?

ELD device data won't run through Tenna's existing ingestion pipeline. Two open questions from Luke's note: does Tenna need to retain the individual point data at all, and if it does, is it processed on the Tenna side or held within the ELD?

A · ELD holds the points The ELD keeps second-by-second telemetry; Tenna receives only derived events and summaries. Exports and audit bundles are served from the ELD.
B · Tenna retains point data Individual points flow to Tenna for processing and retention alongside its other asset data, through a new path rather than the existing pipeline.

Recorded as P3 in the decision log ↗

Then: what crosses the boundary as events
P4

Which ELD-generated events (alarms, exceptions) surface inside Tenna?

HOS violations, approaching-limit warnings, malfunctions, and diagnostics all originate in the ELD. Which of them cross into Tenna's own alarm and notification surfaces, and which live only in the ELD module? The answer decides whether W2 and W8–W10 are the primary surfaces or mirrors of something Tenna-side.

A · ELD module only Compliance events stay in the ELD web module; Tenna users come to it for anything HOS-related. Clean boundary, extra place to look.
B · Push into Tenna alarms A defined subset (violations, malfunctions) publishes into Tenna's existing alert surfaces. One inbox for fleet managers, contract to maintain.
Gates placement of W1W2W8W9W10

Recorded as P4 in the decision log ↗

Finally: where the web module physically lives
P5

Front-end placement: microfrontend inside Tenna's auth boundary, or standalone?

Luke's current thinking: "a microfrontend hosted within our auth boundary rather than a fully standalone app, with seamless access for permissioned users as the requirement." Every web wireframe on this page is drawn inside a Tenna portal shell to make that assumption visible. If the answer changes, the shell changes, not the screens.

A · Microfrontend in the Tenna portal The ELD module renders inside Tenna's web app behind Tenna auth. Seamless for permissioned users; ties releases to an integration contract.
B · Standalone web app A separate ELD site with its own session (linked via P2). Independent releases; one more login unless SSO is built anyway.
Gates W1–W15 · all web screens

Recorded as P5 in the decision log ↗

How to read this page

Every data element is tagged by the system that supplies it.

The point of Thursday's session is pulling data elements out of screens. So every wireframe below carries an annotation panel (purpose, data elements, open questions), and every data element wears one of five tags. The tags are the draft vocabulary for the data guidelines that fall out of the five decisions.

Tenna API

Read on demand from the integration APIs. Working assumption from the kickoff: net-new, purpose-built APIs for this integration rather than direct access to Tenna's existing ones, with on-demand access rather than bulk synchronization as the default pattern.

ELD-owned

Lives in the ELD's own system of record: the certifiable event log and everything derived from it (duty statuses, clocks, edits, certifications, malfunctions).

Tracker · BLE

Read from the Geometris WQ over Bluetooth LE: VIN, odometer, engine hours, position, speed, stored events. Phase 2 measured the stream at ~2–3 s cadence, comfortably inside the FMCSA 5-second engine-sync requirement.

→ Tenna

An event the ELD pushes across the boundary into Tenna (alarms, exceptions, status). Which events make this list is exactly what decision P4 settles.

Gated · P#

This element or screen cannot be finalized until the numbered product decision lands. The wireframe shows one candidate answer so there is something concrete to react to.

Q7

Open questions marked Q# reference the Phase 2 hardware question log: findings from testing the real tracker. Each links to its entry in the decision log.

Reading an entry: the frame on the left is the wireframe, grayscale on purpose, so we argue about content and data, not color and polish. The panel on the right is what the screen needs: its purpose, its data elements with source tags, and the open questions it raises. Screen IDs (D4, W7…) match the Section 5 inventory in the proposal, so the meeting can reference any screen unambiguously.

Sample data is grounded, not lorem ipsum: the vehicle is the Phase 2 test truck (Ford F-150, VIN 1FTFW1R63EFA84339, ~126,500 mi), the tracker is the real unit on it (WQ-87X060680218), and the HOS clocks are a plausible mid-shift afternoon: 11-hour drive limit, 14-hour window, 70-hour/8-day cycle.

Driver mobile app · D1–D26

Nine flows, one hub.

The driver experience centers on D4, the HOS dashboard; almost everything is one tap away from it. Three flows deliberately break that pattern: roadside inspection (D15) is PIN-gated so it cannot be entered by accident, the malfunction notice (D18) interrupts everything when it fires, and carrier edit requests (D20–D21) arrive by push from the back office.
