Certification Roadmap

Tenna ELD · Updated 9/24/2026

1. Basis

  • ELD registration is self-certification under section 5 of Appendix A to Subpart B of 49 CFR Part 395, the functional specifications every ELD is certified against. This page calls it Appendix A. There is no third-party lab, no fee, and no FMCSA-administered test. The certifying statement must describe how the model was tested for compliance with the technical specifications.
  • The reference test method is FMCSA's ELD Test Plan and Procedures, version 2.1 (7/18/2017). It is not binding on providers, but it is the procedure FMCSA uses if it independently evaluates a listed device.
  • Section 4 of Appendix A is the technical specification: what an ELD must do. FMCSA's test plan turns it into a numbered checklist of 347 requirements, each with an ID such as ELD-FUNC-4.6.1.2. The test plan calls that checklist the Requirements Traceability Matrix, or RTM. The requirements fall into eight groups: accounts, vehicle interface, inputs, processing, recording, monitoring, outputs, and data transfer.
  • The test plan also gives step-by-step procedures for testing those requirements, in three chapters. Chapter 1 covers accounts, inputs and the vehicle interface. Chapter 2 covers processing, monitoring and recording. Chapter 3 covers outputs and data transfer.
  • Every piece of test evidence in this roadmap names the requirement ID it proves. We keep the checklist and the chapter order. We do not follow the written steps word for word, because some of them give wrong results on real vehicles. One test may prove several requirements.
  • Malfunction test criteria come from Appendix A Table 4, the list of seven malfunction and six data diagnostic codes, and Table 6, the event type and event code list, on Tom Cuthbertson's review of 9/15/2026.
  • Test plan requirements for the record itself: every step scored pass or fail; report lists date, tester, result, comments, and the re-run set for each failure; regression test after every corrective action; test records retained two years; tests run with multiple driver accounts from different states already created and the driver logged in.

Stage C · Build the ELD

Owner: AppAxis · Phase 3, weeks 4–12

  • This is the main build phase. AppAxis builds:
    • the hours-of-service engine, including all duty rules and exceptions;
    • detection for the seven malfunctions and six data diagnostics in Table 4;
    • the records file that an inspector's system reads;
    • the driver app, run on real phones with real trackers.
  • Each requirement gets an automated test, written at the same time as the code. Test coverage is reported every week.
  • Every build checks the records file against FMCSA's format.
  • AppAxis demos progress to Tenna every week.

Exit. All implemented requirements have passing automated tests. A records file built from live test data passes FMCSA's format check. Evidence: a test report for each release, showing coverage.

Stage D · Transfer and host reporting

Owner: AppAxis · Phase 4, weeks 13–15

  • AppAxis builds the transfer of records to FMCSA. A driver sends them from the truck at a roadside stop. The back office sends them from the control panel, one month at a time. If the truck has no signal, the driver shows the inspection screen on the phone instead.
  • FMCSA accepts records two ways, and AppAxis builds both. Web services: the app's backend sends the file with a client certificate. Email: the backend sends an encrypted, signed message to FMCSA's address with a fixed subject line. FMCSA gives AppAxis a test certificate and sample identifiers before registration, so this work does not wait on Stage F. Certificates and keys stay on the backend, never on the phone.
  • Dependency: Tenna opens the FMCSA provider account before this stage starts. The account is where FMCSA issues the test certificate and sample identifiers, and it holds the file validator and the web eRODS viewer. Registration is a form filed inside the same account later, in Stage F, so nothing here waits on it.
  • AppAxis generates records files all through testing and runs every one through FMCSA's file validator and then its web eRODS viewer.
  • AppAxis builds the full unidentified-driving loop: the tracker records the driving, the truck keeps eight days of it for drivers to claim, the carrier assigns or explains what is left, the assigned driver confirms, and the carrier keeps six months of records. A legal hold stops the six-month purge when a customer's lawyers ask.
  • Every device sends a test transfer to FMCSA once a day to prove the connection works. Three failures in a row raise a malfunction. Test criterion: one failed self-test records data transfer data diagnostic 4, three consecutive failures raise data transfer compliance malfunction S, and both clear on the next successful test.
  • Edits keep the original record and record who changed it. Moving a driving segment from one driver to another needs both drivers to accept.
  • AppAxis builds the host inspector view (W18), a browser view of the same records the driver shows at the roadside on D16. The rule does not require it; eRODS covers the inspector. It is kept because Tenna's customers and auditors can use it, and Tom advised keeping it once built.

Exit. FMCSA's test system accepts transfers sent from the truck and from the back office, on a test fleet. Evidence: transfer confirmations and the test-fleet record.

Stage E · Certification-readiness verification

Owner: AppAxis assembles, Tenna runs the in-truck tests, Tom Cuthbertson accepts · Phase 5, weeks 16–17

  • AppAxis tests the release build with what it has: the automated test suite, the bench trackers and light-duty vehicles. Tests that need a heavy-duty truck fall to Tenna, with AppAxis writing the procedure, joining remotely where possible, and scoring the results. Four kinds of test make up the evidence:
    • Automated: the full test suite runs on the release build and the result is archived.
    • In-truck: Tenna runs FMCSA's test procedures by hand in a commercial vehicle over several days, on the phones its customers use, from step sheets AppAxis provides.
    • Records file: files from those drives pass FMCSA's validator and read correctly in web eRODS, including the hard cases of edit history, driver and vehicle pairings, two drivers on one device, and unidentified driving. Tom's review starts here.
    • Malfunctions and diagnostics: every code in the malfunction test matrix is raised, displayed and cleared, and its records appear in the file. Bench for most; Tenna's truck for the ones that need an engine bus.
  • AppAxis writes the test report in FMCSA's format: date, tester, pass or fail for each step, comments, and what was re-run after each fix. From it, AppAxis drafts the test description for the certifying statement.
  • Tenna writes and publishes the in-cab documents: the user manual, the cab card with transfer and malfunction instructions, blank paper logs, and the user-instructions page that needs no login. AppAxis supplies the technical content: what each screen does, the transfer steps, and the driver's action for every malfunction and diagnostic code. Tom says FMCSA is strict on the manual and the cab card; the FMCSA registry has examples to follow.
  • The certifying statement, development statement, driver manual and cab card are filed in the FMCSA provider account, open since Stage D.

Exit. Tom Cuthbertson accepts the evidence package as enough to sign. Evidence: the package and his written acceptance. Records are kept at least two years.

Stage F · Registration, listing, and maintenance

Owner: Tenna, AppAxis supporting · Phase 5, weeks 17–19, then ongoing

  • Tenna registers the device with FMCSA: provider name, address and contact, the ELD identifier, model name, software version, operating systems, transfer method, the public instructions URL, and the certifying statement that refers to the Stage E test description.
  • One registration and one ELD identifier cover both Android and iOS. The public URL holds the user manual, the transfer and malfunction sheets, and a contact. Still with Tom: which software changes require a new submission.
  • The listing appears within one to five business days. The pilot runs at the same time.
  • After listing, Tenna keeps the registration current. The maintenance runbook covers FMCSA guidance changes, re-submission on major versions, app-store reviews, edge cases drivers report, a yearly user-guide update, and how to respond if FMCSA sends a removal notice.

Exit. The device is listed on the FMCSA registry and the maintenance runbook has an owner. Evidence: the public listing and the runbook.
