This page describes where the ELD ends and Tenna begins. It covers three things: the ELD's own schema in Tenna's Postgres (Contract A), the API the ELD exposes to its mobile app and its portal micro-frontend (Contract B), and what the ELD needs from Tenna's platform (Contract C). The surface codes (T1–T8, E1–E3, B1, S1–S5) and screen codes (D1–D35, W1–W19) are the same ones used on the Wireframes page, so the two pages can be read together.

1. Context

Blue outlines are what AppAxis builds. Grey boxes already exist or are Tenna's to build. The one shared table is users. The ELD reads everything else it needs from Tenna over an API at the time it needs it, and does not keep a copy.

Four rules of the split

  1. Tenna IDs are the join keys. The ELD stores a reference and never copies a Tenna-owned record into its schema.
  2. On-demand reads, not bulk sync. Nothing is copied on a schedule, so the ELD never holds a stale person or asset.
  3. New, purpose-built APIs (T1–T8) rather than direct access to Tenna's existing ones, each scoped to what the ELD needs.
  4. The certifiable record stays in the ELD schema. Tenna receives copies of events (E2), never the authoritative record.

Assumptions

  • The ELD API is deployed in Tenna's AWS account, in the VPC that can reach the Tenna Postgres instance.
  • Runtime, framework and API gateway are Tenna's choice. They are placeholders in section 7 until Tenna fills them in.
  • A Cognito JWT from the shared user pool is the bearer credential for both the mobile app and the micro-frontend. The ELD API validates it with the pool's public keys and reads carrier and role claims from it.
  • Driver events are never lost by design: the transactional outbox pattern is used on the phone and on the server (section 4). This is a design requirement, not a setting.
  • The ELD backend lives in a repo Tenna owns, alongside the micro-frontend repo P5 already calls for. To be confirmed.

3. Contract A: the ELD schema

Postgres, schema eld, in Tenna's instance. Most of these tables come straight from what the two native apps already store. Each event the apps write today has a per-driver sequence number, a type and code, a timestamp, odometer and engine hours with flags that say whether each value was read or estimated, a location, an origin, and a notBefore time when the change happened somewhere inside a gap in the tracker data. Unidentified driving comes off the tracker as pairs of events identified by reason code and device time. The apps only implement event types 1, 2 and 6 so far. Types 3, 4, 5 and 7, and edit versioning, are new. Those tables are proposals, not copies of working code.

Solid arrows are foreign keys inside the eld schema. Rows typed "text · Tenna" hold a Tenna user, carrier or asset id stored exactly as Tenna issued it; the ELD reads the record through T2, T3 or T4 when it needs a name, and there are no foreign keys into Tenna's tables and no joins across the schema boundary. Tenna can change its own schema without touching the ELD. The shared users table is the one exception to the split, and even there the ELD keeps only the id. Column lists show the keys and the columns that matter for the relationships; the full lists follow below.

  • Every write that must reach Tenna (E2, E3) inserts its outbox row in the same database transaction as the business row. Either both commit or neither does, so there is no window in which an event exists but its notification was lost, and no window in which Tenna is told about an event that was rolled back.

Cross-cutting rules

  • Every timestamp is timestamptz in UTC. The apps use epoch milliseconds UTC everywhere. The tracker's UDRV_TIME and LOCTIME are epoch seconds on the device clock and are kept in their own columns where they matter.
  • Event time comes from the tracker's GPS time, cross-checked against a network time source; the user-settable phone clock is never the source (4.3.1.5). A deviation over 10 minutes from UTC is a timing malfunction.
  • Home-terminal time zone is read from T3 for display and for the 24-hour certification boundary. It is stored on certification events as the offset in effect, and nowhere else.
  • Tenna ids are stored as text exactly as Tenna issues them. The ELD never parses them, checks their format, or joins on them. No foreign keys into Tenna's schema and no cross-schema joins. Names are resolved at read time through T2 and T4.
  • Tenant isolation is carrier_id on every table. Row-level security keyed on the JWT's carrier claim is the recommendation; the API enforces it regardless.
  • Ids are UUIDv7 everywhere. The leading 48 bits are a millisecond timestamp, so ids sort by creation time and a B-tree index on them grows at one end instead of splitting randomly. Generators must use a monotonic counter for ids created in the same millisecond. On the phone the id is stored as a 16-byte blob. The id is for dedupe and index locality only; the per-device seq remains the order of record.
  • No request handler talks to Tenna or FMCSA directly. Anything that leaves the ELD is written to eld.outbox in the same transaction as the row it concerns and sent by the relay.
  • JSON contract: the apps' session JSON distinguishes a missing key from an explicit null. The API normalizes inbound payloads to explicit nulls before validation, so the schema never has to model "absent".

REST over HTTPS, JSON bodies. Bearer token is the Cognito JWT from the shared pool. Base path placeholder /eld/v1. Grouped by who calls it.

Never losing a driver event: the outbox pattern at both hops

A driver event can be lost at two hops: between the app recording it and the network, and between the ELD API storing it and anything downstream. Both hops use the transactional outbox pattern, so a record and the intent to deliver it are always written together.

HopTransactionRelayIdempotencyOn failure
Phone to ELD API (E1) The event row in the on-device log and its outbox entry are written in one SQLite transaction (Room on Android, GRDB or SQLite directly on iOS). The UI never shows an event that is not already queued A sync worker reads the device outbox in seq order, posts batches of up to 200, and deletes an entry only when the server says accepted or duplicate. Backoff on failure. Survives process death, reboot, airplane mode, and the OS killing the app for background CPU Event id (UUIDv7), assigned on the device Visibly. An entry older than 24 hours or rejected by the server raises the recording diagnostic on D18 and is listed in W10. It is never dropped; a driver can see the count of unsynced events on D4

Device time is authoritative for at_utc; the server stamps received_at. If the two differ by more than 60 seconds at receipt, the server records a diagnostic note on the batch and the phone raises the timing check (malfunction category T) if the skew persists.

An idempotent batch, end to end:

  1. The app records an event, assigns the next seq for this device (one counter for every driver on the phone), and in one local transaction writes it, the counter, and the outbox entry with a UUIDv7 id.
  2. The sync worker takes up to 200 outbox entries in seq order and posts them as one array to /events with the JWT.
  3. The server validates the JWT, checks the carrier claim against every row, and in one Postgres transaction inserts each event with ON CONFLICT (id) DO NOTHING together with any eld.outbox rows the event implies.
  4. The response marks each id accepted or duplicate, and lists any seq gaps it now sees for that device.
  5. The app deletes accepted and duplicate ids from its outbox. Rejected ids stay and surface on D18 as a recording diagnostic.
  6. If the connection drops before the response, the app retries the same batch. Step 3 makes the retry harmless.
  7. The server relay publishes the new outbox rows to Tenna and marks them published on acknowledgment.

  • Roadside transfer (D17): web service first, email co-equal. The officer's code goes in the output file comment. The receipt or error is stored on the transfer row either way.
  • Transport, per FMCSA's ELD Data Transfer Requirements sheet (9/10/2026): web services is a SOAP call carrying the client certificate, the output file and the comment, with a test flag; email is S/MIME, AES-256 encrypted to FMCSA's public key and signed with the provider's private key, subject "ELD records from <registration id>:<ELD identifier>". Both keys live in the ELD backend's secret store, never on the phone. FMCSA issues a test certificate and sample identifiers before registration.
  • Host-initiated transfer (W17): the same generator behind the same transfer-requests resource, capped at 30 days per request, split automatically into increments the eRODS endpoint accepts. Filterable by driver, vehicle and period (4.9.2).
  • Transfer self-test (4.6.1.7): the device submits a TEST-flagged file of its real log every 24 hours, automatically, with "24-hour test" in the output-file comment (Tom Cuthbertson's cadence, Q30; the rule's floor is every 7 days). Three consecutive failures raise a data-transfer malfunction. Attempts are eld.transfers rows with method selftest; state shows on W10 and lights the D19 indicator.
  • Driver's own records (4.7.2): POST /drivers/me/record-requests generates the driver's output file for a chosen range and emails it to the address on the Tenna user record. The phone never handles the file. Delivery channel is a product decision pending Sunil.

Conventions

  • Errors. RFC 9457 problem details: type, title, status, detail, plus a per-item errors[] on batch endpoints.
  • Pagination. Cursor-based, ?cursor&limit, limit capped at 500.
  • Versioning. Path version (/v1). Additive changes do not bump it. The mobile app sends its version in a header so the server can refuse a build that is too old.
  • Rate limits. Per device for E1, per user for the micro-frontend. Generous, because the phone sends in batches. A 429 includes Retry-After and the queue waits that long.

6. Key flows

Lifelines are Tracker, Phone (the ELD app), ELD API, Tenna, and FMCSA where relevant. Each hop names the contract that handles it.

Flow 1 — Pairing and first drive

  • The serial in the advertised name is the only key the phone has before it connects. T4 resolves it to an asset; if T4 returns nothing, D2 shows the serial and refuses to pair.
  • With the ignition off, the VIN item is empty (Q3). The cross-check runs on the first frame that includes one, which is the first drive, not pairing.
  • A mismatch does not block recording. The event stores vin_observed and the roster (W11) shows the flag until someone fixes the asset record in Tenna.
  • Hops: B1 for everything to the tracker, E1 for the phone to the API, T4 for the API to Tenna.

Flow 2 — Drive detection and sync

  • The ELD decides motion and stops from the speed item. Driving begins above 5 mph. A stop is suspected after three seconds at zero speed. A yard move ends by itself above 20 mph and records Driving, with no prompt (Tom Cuthbertson 9/14/2026, Q29); a yard geofence may end it earlier.
  • Every event is created and sequenced on the device before it is sent, on one counter shared by every driver on that device (4.4.4.1). The host never assigns seq and never reorders.
  • The event and its outbox entry are one local transaction, so an event the driver can see is by definition an event that will be synced. The device outbox is drained only on server acknowledgment.
  • A rebuild after a lost phone is a read from the host, which is why P3 requires every event to reach the host when recorded.
  • Hops: B1, then E1. Nothing in this flow touches Tenna.
  • Motion without sign-in (D35). If the phone's GPS says it is moving, an advertising tracker is in range, and this lasts past the threshold, the app shows the sign-in-or-decline screen. The tracker keeps recording as unidentified driving regardless; this is a prompt, not a record.

Flow 3 — Certification

  • The 24-hour period is defined in the home-terminal zone read from T3, which is why that zone is never stored on the event.
  • A certification is itself a type 4 event with a seq, so it appears in the output file in order.
  • Whether Tenna hears about certifications at all is on the P4 list.

Flow 4 — Edit proposal and annotation

  • The API refuses, at proposal time, any change that would shorten or reassign automatically recorded driving time. The one exception is ending a drive segment at a power-down the device missed.
  • Wrong-driver reassignment is two proposals, one to each driver, and takes effect only when both accept.
  • The push to the driver is host-originated. Whether it goes through the ELD app's own push channel or Tenna's engine is part of P4. The data path does not change either way.
  • Hops: micro-frontend to API (Contract B), API to phone (push, then E1 for the decision), API to Tenna (E2).

Flow 5 — Unidentified driving

  • The purge interlock is the rule that matters most: 0x0103 is destructive and unacknowledged, so the phone sends it only after the host has accepted every drained key. A phone that dies mid-drain re-drains and the natural key makes the repeat harmless.
  • The five fixed carrier reasons plus carrier additions come from S5. An assignment to a driver is pending until that driver accepts at D34.
  • The same table serves the 8-day in-cab list on the phone and the 6-month host record. They are two views, not two stores.
  • Hops: B1, E1, Contract B for W16, push then E1 for D34.

Flow 6 — Roadside and host-initiated transfer

  • The file is generated on the host from the host's copy of the log, which is complete because of P3. The phone only needs to be able to reach the API.
  • With no signal, D16 shows the 8-day record on the phone in the FMCSA display format and the inspector reads it there. The session is still logged.
  • Failed transfers are compliance records. The transfer row and the outbox row that drives the attempt are written together before anything is sent; the relay updates the result. A crash mid-transfer resumes from the outbox instead of losing the request.
  • Hops: E1 for D17, Contract B for W17, the eRODS web service and email for FMCSA.

Mobile app

Native Swift and Kotlin. Module layout as built in the two ports: domain (protocol parsing, HOS state machine, event records, no platform imports), services (BLE transport, tracker service, session log, sync queue), app (screens). Invariants from the READMEs that matter to Tenna because they explain why the code looks the way it does:

  • One SQLite database per install (Room on Android, GRDB on iOS), WAL mode, written only from the service thread. Tables mirror the server names where they overlap: readings, events, outbox, ud_records, power_events. Rolling retention is a daily delete by timestamp. The session JSONL used for test evidence is exported from it, not written alongside it.
  • Single-thread confinement for everything service-side. BLE callbacks are marshalled onto one serial executor, so the state machine never sees two events at once.
  • The session log and the device outbox are append-only and durable, written in the same local transaction. Nothing is rewritten in place on the device, and nothing leaves the outbox without a server acknowledgment.
  • The purge interlock: the tracker's stored unidentified driving is purged only after the host acknowledges every record.
  • Frame assembly tolerates a tracker that sends garbage; a zero-count header is discarded, never indexed.
