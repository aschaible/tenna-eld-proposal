How the big four ELDs
actually build their driver apps.

The proposal recommends React Native with strategic native modules for the Tenna ELD driver app. This brief establishes what Samsara, Motive, Omnitracs, and Geotab run in production, from engineering blogs, live job listings, public SDK repositories, and published package sizes. Every claim links to its primary source. No analyst commentary, no inference without the receipts.

Original

You are reading the original evidence brief. A revision dated 8/28/2026 narrows the native-module scope by one item, following the August 17 FMCSA compliance review. A further revision dated 9/2/2026 notes what the 28 August huddle settled about authentication and the host surface. Switch versions with the control at the bottom right.

Revision 8/28/2026 · one narrowing

The August 17 FMCSA compliance review established that an ELD certifies for one data-transfer family: telematics (web services and email) or peer-to-peer (USB and Bluetooth to the inspector's device), never both. The build elects telematics, so USB transfer leaves the native-module list. What remains needing native code is Bluetooth pairing and background ECM polling.

That does not change this brief's conclusion; it slightly strengthens it. The native surface the recommended approach has to carry gets smaller, which is the argument for React Native with targeted native modules rather than against it. Every competitor finding below stands as documented; note that Motive's job listings still place USB integration in native code, which is consistent with a different transfer-family election, not with ours.

Revision 9/2/2026 · one note

The 28 August huddle settled two things that touch the stack. Sign-in is a native form in the app against Tenna's existing Cognito pool through the Amplify SDK, rather than a hosted page the app opens in a browser, which keeps authentication inside the React Native surface and off the native list. The host module is a micro-frontend inside the Tenna portal on a shared component base, which is a web concern and does not touch the mobile stack at all. Neither changes the recommendation.

Dossier 01 · Samsara

Samsara

Enterprise telematics · NYSE: IOT
React Native + Native Modules Confidence: Documented first-party
Architecture React Native for the mobile codebase, Go for code running on Samsara-controlled hardware, React with TypeScript across web and mobile UI layers. Native modules used selectively for performance-critical paths.

Samsara is the only one of the four that documents its mobile architecture in public, in detail. A 2022 engineering blog post by Andrew Monks, a Staff Software Engineer on the team, describes both the architectural choice and the deliberate rewrite the team undertook in 2019 to stay on React Native rather than transition to native. When a 64-bit Play Store deadline forced an architectural decision, Samsara considered native Android and explicitly rejected it, because the cross-platform contribution model that React Native enables was worth preserving. Roughly half of the Driver App codebase is now shared infrastructure (logging, offline reconciliation, navigation, auth, storage, Code Push, component library) that powers four additional mobile apps in their ecosystem.

The choice reflects organizational structure as much as technology. React Native lets Samsara's feature teams contribute to mobile without dedicated iOS or Android specialists, and the company has shipped five customer-facing mobile apps from the same React Native foundation.

We love how it lets us structure our teams autonomously, and everyone can contribute to mobile, with engineers building features that work for both Android and iOS without a lot of overhead." Dossier 02 · Motive

Motive

Market leader · formerly KeepTruckin
Pure Native · Two Codebases Confidence: Hiring signals, unambiguous
Architecture Native iOS in Swift and Objective-C with MVC, MVVM, and VIPER patterns. Native Android in Kotlin with Kotlin coroutines, Kotlin flows, RxJava2, and Dagger2. Two fully separate codebases, no shared cross-platform layer.

Motive does not publish architecture decisions, but its active Greenhouse job board makes the stack unambiguous. Multiple current and recent listings for iOS Engineer, iOS Platform Engineer, Senior iOS Engineer, and Senior Mobile Engineer iOS all require Swift and Objective-C proficiency along with native iOS architectural patterns. The Android listings require Kotlin coroutines, Kotlin flows, RxJava2, and Dagger2, all signature native Android tools with no React Native equivalents.

The tells are specific. VIPER is a native iOS architectural pattern. RxJava2 and Dagger2 are native Android libraries. Kotlin coroutines and flows are Kotlin-only constructs. None of these appear in a React Native codebase. The role descriptions also place GPS, Bluetooth, USB, and Camera API integration in native code, consistent with the two-codebase model. Motive sustains this approach because it has the engineering scale, more than 50 mobile engineers across both platforms, to make duplicate native work economically tractable.

Dossier 03 · Omnitracs

Omnitracs

Legacy incumbent · Solera-owned
React Native for New Builds Confidence: Hiring signals, explicit
Architecture React Native for current and new mobile development under Solera ownership. Native iOS (Objective-C, Swift) and native Android (Java) maintained where necessary, including performance-critical native bridges. Legacy products on the older IVG device run Windows, with an Android variant in testing.

Omnitracs operates an active engineering team in Mexico City building under the React Native model. The public listing for React Mobile Software Engineer II is unambiguous about technical direction: the role builds new mobile applications in React Native, while requiring native iOS and Android experience for the bridge and platform-specific work. The team maintains Sylectus, the Solera-owned TMS mobile application, alongside new React Native builds across the logistics product line.

The legacy picture is more mixed. The older Intelligent Vehicle Gateway hardware platform ran Windows for years, with Android support added later, and Omnitracs One has been the consolidation effort bringing the product suite onto modern mobile tooling. The strategic direction under Solera is clearly toward React Native for new mobile work.

Dossier 04 · Geotab

Geotab

Telematics platform · largest installed base
WebView Hybrid Confidence: Triangulated, four independent signals
Architecture A single web application (HTML, CSS, JavaScript) for the Geotab Drive interface, loaded inside thin native shells written in Swift on iOS and Kotlin on Android. The shells handle Bluetooth pairing, foreground services, location, and bridge APIs for what a WebView cannot reach.

Geotab publishes no single architecture statement, but four independent signals triangulate convincingly. First, Geotab's own Mobile SDK on GitHub: the iOS SDK is 94.5% Swift and 5.5% JavaScript, the Android SDK 95.5% Kotlin and 4.5% JavaScript, and both repositories describe their entry point as the container for the Geotab Drive web application. Second, the package math below. Third, Geotab's Add-In system loads the same HTML, CSS, and JavaScript into both the MyGeotab web portal and the Drive mobile app, which is only architecturally possible if the mobile app is fundamentally a WebView rendering the same web environment. Fourth, Geotab's own documentation refers to "the web version of the Drive App" as a variant of the same product, consistent with one shared codebase rendered in different shells.

The package math

Native apps with a comparable ELD feature scope (full HOS state machine, DVIR, eRODS roadside transfer, Bluetooth pairing, eight-day record cache, malfunction handling, UI) typically weigh 50 to 150 MB. A 3 to 5 MB package cannot contain a native UI for that feature set. The math only works if the UI loads at runtime from the network.

The Take · What This Means For The Tenna Build

The recommendation sits in the industry mainstream, by evidence rather than convenience.

3/4
Leaders avoid full native

Samsara picked React Native deliberately and reaffirmed the choice through a documented rewrite. Omnitracs is migrating new builds to React Native under Solera. Geotab chose a WebView hybrid that maximizes web-codebase reuse. Only Motive runs pure native on both platforms, and Motive has more than 50 mobile engineers to make duplicate work economically tractable. Three of the four avoid full native because the team-size cost is meaningful at any scale.

The Samsara parallel is the operative one

AppAxis proposes this build with one dedicated mobile engineer alongside a backend engineer and QA, which makes the Motive model structurally inaccessible. The Samsara model, React Native with native modules for performance-critical paths, is the most directly comparable approach and the one this proposal recommends: native code precisely where Bluetooth pairing, background ECM polling, and USB transfer demand it, shared code everywhere else.native code precisely where Bluetooth pairing and background ECM polling demand it, shared code everywhere else. As of the 8/28 revision USB transfer is no longer on that list: electing the telematics transfer family removes it from the build entirely.

The Geotab precedent, noted and declined

Tenna already operates a web application at app.tenna.com, so the Geotab pattern of wrapping a web codebase in native shells has a real precedent worth acknowledging. The tradeoffs are also real: weaker UX polish, more fragile offline behavior, and a riskier Apple App Store review posture for a safety-critical application whose roadside inspection mode must render in under 5 seconds without a network. For an ELD, those tradeoffs run the wrong way.

The conclusion

React Native with strategic native modules places the Tenna ELD in the mainstream of modern ELD mobile architecture, alongside Samsara and Omnitracs's new builds. The choice is defensible on industry precedent, not just on team economics. Back to Section 4 of the proposal for how the recommendation is structured.
